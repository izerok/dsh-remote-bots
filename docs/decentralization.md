# 去中心化路线：能不能像 EasyTier 一样

> 研究日期 2026-11-22，基于 zen-remote 2.5.4 源码与 EasyTier 上游 README。完整研究报告（含逐条源码出处）在本地测试目录，未入仓。
>
> **当前状态：研究已完成，实施已暂停。** 网关落点（家中主机还是 NAS）待用户拍板，见文末。

## 结论先行

1. **zen-remote 本身不是一个中心化服务。** 它分三条路：host/client 走每台 host 自带的 lan-gate + 你自己的反代；peer 走自建 gateway-server + UDP 打洞，**直连优先、网关只中转密文**。数据面去中心化的程度，已经和 EasyTier 是同一形态。
2. **真正的中心点只有三处，而且其中两处已经是你自己的机器。** 一是每台 host 上的 lan-gate（配对 + 反代 + 中继标记，自建）；二是 peer 模式的 gateway-server（信令 + 准入 + 打洞协调 + 兜底中转，自建 Docker，零知识）；三是 Web Push 的厂商推送服务（APNs/FCM），这是唯一一个第三方、且去不掉的。
3. **“像 EasyTier 一样”最缺的不是直连能力，而是发现与信令。** EasyTier 的节点只要知道任意一个网内地址就能入网，没有注册表；zen-remote 的 peer 入网必须先连上 gateway-server，由它广播成员、协调打洞、审批准入。直连的路已经修好了，修的是“怎么找到对方”。

## 现状的中心化点（5 个）

| # | 中心点 | 第三方程度 | 说明 |
|---|---|---|---|
| C1 | 公网入口（反代/域名/CF Tunnel） | 中 | 手机与外网 client 唯一的进门方式；反代自建，域名与 CF Tunnel 是第三方依赖 |
| C2 | lan-gate（每台 host 一个） | 低（自建） | 配对、令牌、反代、中继标记头全经它；per-host，没有“总网关”，但单台 host 的远程入口全系于它 |
| C3 | 中继协议的网关密钥门 | 低（设计） | DSH 中继路由要求 `x-zen-remote-secret` + `via: gateway` + `role: desktop-client` 三件齐全，直连绕过 lan-gate 会 401；EasyTier 换“路”换不掉这道“门” |
| C4 | gateway-server（仅 peer 模式） | 低（自建） | peer 网唯一的中心：信令、五态准入、STUN 打洞协调、兜底中转；零知识（只见 28B 路由头 + 密文），已直连的会话不受它宕机影响 |
| C5 | Web Push 厂商服务 | 高，且去不掉 | 投递路径必须经过 APNs/FCM；VAPID 密钥是你自己的、payload 端到端加密、默认不带对话内容 |

补充：Bots 数据（roster/记忆/workspace）只在 host 单机，这是**数据单点**，不是传输中心点，换传输层解决不了它。

## 三条路线

### A：EasyTier 虚拟网当传输层（只改部署，不动代码）

所有设备进同一个 EasyTier 网络，host 的 lan-gate 改绑 `0.0.0.0`，client 配对时填 host 的虚拟 IP。能去掉桌面与手机数据面的公网入口（C1），但**去不掉 lan-gate**（C3 的密钥门要求请求必须经 lan-gate 盖章）。

代价：每台设备都要跑 EasyTier；手机需常驻 VPN（iOS 同一时间只有一个 VPN 隧道，会顶掉 Stash 代理与 LocalDevVPN）；**手机 PWA 在 `http://10.x` 上装不了**（Service Worker 要求安全上下文），推送也丢。建议手机保留公网域名入口、只把桌面流量迁进 EasyTier。

### B：网关降级为纯 fallback（peer 模式已基本实现；补齐是把 client 换成 peer + 网关自建落地）

桌面之间改用 `role: peer` 加入自建网关的网（`zr-net://` 邀请链接），网关 Docker 部署在家中主机或 NAS。直连优先已是 peer 引擎默认行为（1000ms 打洞窗口，`lan` → `p2p` → `relay`，打通后热切回直连）。不改代码。

能去掉桌面流量的公网入口（C1）与网关的中转角色（C4 只剩信令与兜底）。代价：网关挂了则新节点入不了网、打洞没人协调；需要开 UDP 端口；入网要过审批或口令。

> **⚠️ 安全前置（2026-11-22，zen-remote 2.5.2）**：切 peer 角色之前，必须先在授权表里显式写死 `pluginBridgeConsent: {"@kadaliao/dsh-bots": false}`（或确认网内全是可信设备），切完用 `admin/plugin-bridge` 核对实际生效值。原因：peer 角色下，授权表里没写过的已登记插件对网内 peer 设备默认就是同意的（`effectivePluginConsent`，`src/index.ts:846-858`；CHANGELOG 2.5.2：“`peer:` 组网节点默认放开未显式关闭的整机插件权限”）。不钉死就切，bots 面板（整机数据、可删 Bot、可改 key）会对网内每一台 peer 设备默认敞开。去中心化实施本身仍暂停，这条只是实施时的硬性步骤。

### C：去掉 gateway-server 信令（改上游代码，fork 维护）

peer 引擎的信令改走 EasyTier 网内直连，或给中继加直连模式放宽三道门。能去掉 C4 全部，但改动面大（peer 引擎约 5 个核心文件 + 中继两端 + 测试集），要 fork zen-remote 长期跟上游，且安全模型须重审（网关密钥门是防本机其他进程伪造标记头的关键设计）。**不推荐现在做**：B 做完后网关只剩信令与准入两项轻职责，为去掉它而 fork 整个插件，性价比低。只在“连自建网关都不想留”成为硬性要求时再立项。

## 推荐：A+B 组合，分两步走

1. **先 B**：桌面改 peer 角色，网关自建落地。桌面流量默认走局域网直连或 UDP 打洞，网关只剩信令与兜底中转，且网关是你自己的、看不到任何会话内容。
2. **再 A 的桌面部分**：桌面设备再进同一个 EasyTier 网络，作为 peer 直连之外的第二条路。手机不迁：PWA 与推送仍走现有公网域名入口；手机同时进 EasyTier 网可作为备用网页入口（HTTP，不装 PWA）。

## 不能去中心化的部分

- Web Push 不经过厂商服务：协议规定投递走浏览器厂商的推送服务，没有自建推送能到达 iOS 锁屏。
- PWA 安装不用 HTTPS 受信证书：浏览器只给安全上下文注册 Service Worker；自签证书 iOS 不认。
- 首次信任零相遇点：配对码、邀请链接、网络密钥总要带外交换一次；相遇点可以是本地的，不需要中心服务器。
- NAT 打洞零协调方：打洞需要第三方交换候选地址；协调方可以是自建的，“有没有”去不掉，“是谁的”可以自己定。
- Bots 数据多机同步：roster、记忆、workspace 只在 host 落盘；要做需另起数据层，工作量与风险都大一个量级。
- 吊销即时到达所有节点：没有中心广播，吊销只能靠 gossip 或下次握手时发现；接受最终一致 + 短期令牌。

## 待用户拍板（三件事）

1. 网关落点：家中主机还是 NAS；
2. 手机入口：保留公网域名（保 PWA/推送），还是接受 HTTP 网页版进 EasyTier（丢 PWA/推送）；
3. 是否接受“网关是你自己的、零知识”这个剩余中心——如果接受，路线 C 永久不需要做。
